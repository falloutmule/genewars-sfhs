# Campaign audio request and device boundary

The simulation keeps a serializable bounded request journal. `requestAudio(state,request)` retains the existing play/stop request shape and source mode. Optional `initialRatePercent` supplies an explicit initial sample rate; omitted values retain the browser's100% default. The legacy `range` field remains compatible and is never inferred to mean a rate.

`requestAudioPlaybackRate(state,{frame,entity,cue,ratePercent})` appends a distinct `type:"playback-rate"` control with the shared sequence counter. It has no play mode, volume, source URL or invented start behavior. `AudioEventRequest` is the union of legacy `AudioRequest` and `AudioPlaybackRateRequest`; `AudioState.requests` stores this union. The source reads signed SI, so the control admits signed16-bit values. Nonpositive values have no device effect. An initial rate must be positive. Invalid inputs leave the sequence and journal unchanged, and the existing256-request retention applies across both event types.

Source98210 checks audio device/settings gates, then finds the already playing sample with matching entity identity and channel. It requires status4 and a positive changed signed rate percentage. It changes sample frequency to `baseSampleRate * ratePercent / 100` and stores the new percentage. Its ECX argument is unused. Reward59/0x3B supplies500, meaning five times base sample frequency; there is no corresponding new play mode or spatial range operation.

`CampaignAudio` is a read-only journal consumer. It applies each new sequence once. A rate control only changes the matching currently playing `HTMLAudioElement.playbackRate` to `ratePercent/100`; it cannot create, restart or select another sample. This replaces the prior percentage rather than multiplying it. Missing, ended, paused, disabled or nonpositive updates do nothing. Equal device rates avoid redundant writes. Source frequency changes alter pitch and duration together, so `preservesPitch` is false for source samples. A browser's unsupported rate is ignored without clamping to an invented source value. Autoplay rejection, device rate limits, mute/pause/resume and render timing never modify requests or gameplay. Stop mode4 still stops/removes the matching device sample, and reset discards prior device identities before consuming a loaded journal.

Source76620 remains a separate narration/message queue and latch service. It checks global118968 bit0, the per-cue byte at its supplied base (reward uses11C21A), global185EC3 bit2/force BL and the special cue46 latch. On admission it sets the cue byte and calls2F880 with the corresponding116308 table entry. Reward selected-player cues3A/3B must remain pending typed presentation events until that queue/latch/device service is bound. They are not translated into guessed WAVE requests.

Seven focused synthetic tests use a fake device to verify legacy request compatibility, explicit initial rates, a mode-free serialized control, validation/retention, exact entity/channel matching, source ordering, absolute rather than compounded rates, paused/ended/missing cases, pitch behavior, reset, unsupported-rate handling, autoplay rejection and unchanged journals. Read-only evidence is preserved `landing-contact/instructions-00098210.txt`, `font-menu-state/instructions-00076620.txt`, and the reward callback's original call arguments. This boundary does not claim full original audio mixing, spatial attenuation, narration scheduling or device acceptance.
