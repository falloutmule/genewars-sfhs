# Conditional audio intent and device playback

`AudioIfPlayingStopPlayRequest` records one serializable source97830 condition followed by an ordered stop/play pair. `requestAudioIfPlayingStopPlay` appends it to the existing audio sequence and256-entry journal. The record contains flat scalar fields only: frame, entity, queried/stopped cue, next cue, parameter, range, gain and an optional explicit initial rate. It contains no observed playback status, resolved actions, play mode or nested mutable action list. Invalid fields are rejected before the journal changes; unrelated input fields are not copied.

The Extractor source branch queries its building/cue47(0x2F) at46B90. When the device reports playing, it stops47 at46BAC and plays48(0x30) at46BC3, using mode2,parameter0,volume80 and range100. These requests precede any same-callback work-start47. The pure caller can represent that intent with cue47,nextCue48,nextParameter0,nextRange100,nextGain80/127. This family supplies the typed journal and consumer; it does not activate a new Extractor callback, event binding, profile or pack.

`CampaignAudio.consume` processes the intent once at its ordinary numeric-journal position. It checks the current exact `entity+":"+cue` device, requires audio enabled and not suspended, and reads its `ended`/`paused` state once. A matching unended, unpaused device permits both actions. Stop removes that device first; the following ordinary play uses the existing preferred-format lookup, volume/rate handling and allocator. The stop is retained if the next sample is missing or device creation/play fails. No second status query can suppress the play after the stop. No device result or resolved request is appended to campaign state, and the two internal actions allocate no additional journal sequences.

The existing private device helper also handles ordinary play/stop entries. Numeric cues, voice allocation, playback-rate controls, pause/resume, reset and device cleanup retain their behavior. Autoplay rejection, media errors, sample completion, shared-slot replacement and explicit stop remove actual device records; a prior play request alone is not evidence of active playback. The Botanist adapter's existing historic presentation policy explicitly selects ordinary play/stop requests and ignores both rate controls and this new conditional intent. It does not query device state or change Botanist gameplay.

Saves and headless replays retain the deterministic intent. Live, missing, ended or muted consumers may produce different sound while leaving the complete campaign, RNG, journal and checksum identical. Mount/load/reset disposes current devices and skips historical journal entries; it does not reconstruct a loop from an old save or infer its status. The app consumes numeric audio only when active/unpaused, then consumes its separate voice batch. A long pause or headless advance can overrun the existing journal retention. This is a defined conversion presentation boundary, not original device timing or hardware equivalence. Existing limits for41780 per-cue caps, deferred-stop polling, spatial mixing/attenuation and ordering against the separate voice batch remain unchanged.
